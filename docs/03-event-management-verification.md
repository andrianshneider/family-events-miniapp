## Поведение

- «Другие действия с событием» → «Удалить событие» → название и предупреждение о ссылке/необратимости → Отмена/Удалить. До подтверждения нет мутации. Нативный dialog удерживает фокус, Escape/Telegram Back закрывают его, после закрытия фокус возвращается к исходной кнопке. Во время запроса закрытие и повтор блокируются; Telegram получает closing confirmation. Offline отключает удаление, ошибка/status имеют текст.
- DELETE требует действующую сессию, Origin + CSRF, строгий UUID, strict `{expectedVersion}` и Idempotency-Key. Principal только серверный. Чужая/несуществующая запись всегда 404.
- Сначала блокируется Event владельца, затем проверяются receipt и версия. Функция soft delete устанавливает `deleted_at`, `updated_at`, увеличивает version, отменяет active reservations с `event_deleted`, выключает/revokes subscriptions и отменяет pending/processing outbox с очисткой lease. RSVP, Wishlist, Gifts, EventChanges и media сохраняются. Новая миграция 007 заменяет две функции, не добавляет таблиц и не меняет применённые миграции.
- Повтор той же операции возвращает прежний 200 receipt. Собственное уже удалённое событие с новым валидным key возвращает 200 `{deleted:true}` без повторных side effects; версия запроса для уже удалённого объекта не требует совпадения. Повтор key с другим payload — 409. Чужое удалённое событие — 404. Receipt живёт 24 часа; после истечения собственный tombstone позволяет подтвердить результат новым key без мутации.
- Timeout/ошибка сети/неопределённый 500 сохраняют прежний key и expectedVersion в памяти; «Проверить удаление» повторяет прежний запрос. GET 404 не используется как доказательство успешного удаления. После перезагрузки память операции теряется; удалённый объект показывается как недоступный, без неподтверждённого success. Повторного автоматического DELETE после входа нет.
- 409 VERSION_CONFLICT закрывается явной загрузкой текущих сведений и повторным подтверждением; более свежие данные не перезаписываются. Success делает полный переход к свежему SSR `/events?deleted=1`, показывает «Событие удалено», активный список/empty state уже из БД.
- Открытая страница управления перепроверяется при visibility/pageshow/online и каждые 15 секунд, когда видима. Открытая edit-форма — при возвращении и каждые 30 секунд; чужой аккаунт, expired session, удаление и новая версия обрабатываются без автоматической отправки. Ввод при version conflict сохраняется; удалённая форма закрывает сведения и действия. Пока confirmation открыт, фоновое обновление management не уничтожает диалог и не теряет проверку неопределённой операции.
- После подтверждённого save/delete BroadcastChannel передаёт только invalidation hint без данных и credentials: другие видимые вкладки перечитывают сервер. При недоступном канале остаются periodic/restore проверки.
- Список сохраняет SSR, пагинацию, пакетные signed thumbnails и фоновые 90 секунд; восстановление pageshow/visibility/online перечитывает активные события. Offline/background error сохраняет ранее загруженные сведения с retry; актуальность офлайн не гарантируется.
- Все существующие event-specific GET/PATCH/edit/cover маршруты проверяют deleted filter. Публичный маршрут в текущем приложении только cover; публичная Event Page ещё не реализована. Generic media preview закрыт для обложки, связанной только с deleted Event; если файл используется другим активным Event/Gift, он остаётся доступен своему владельцу. Физические файлы не удаляются. Уже выданные signed URLs действуют до TTL (cover 60s, list thumbnail 120s), мгновенный отзыв/удаление сторонних превью не обещается.
- Reservation DB-функции уже берут event lock перед gift/reservation, поэтому reserve/delete сериализованы. Subscription guard теперь блокирует Event и перепроверяет deleted state перед opt-in. Будущие RSVP/Gift/notification mutations должны соблюдать контракт event → children → subscriptions/outbox; соответствующие публичные mutation API ещё отсутствуют. Retention/purge/restore не запускаются.

## Расхождения источников и границы

- Экран 05 требует будущую дату и возврат в список. Задание явно сохраняет Technical Specification: прошлые события редактируются, save возвращает к актуальному «Моему событию».
- Audit snapshot включает eventDate/startTime/endTime/timezone/venueName/address; состав будущего предложения N3 на экране 05 уже (date/start/venue/address). Различие зафиксировано: пока лишь сохраняем snapshot, не внедряем диалог/автоматическую рассылку.
- Без подписчиков значимый save → skip + decided_at; с подписчиками → pending. title/type/description/dress/cover и краевые пробелы не создают snapshot. Save и snapshot атомарны; один key не создаёт повторный change.
- Изменения отменяют устаревшие pending N4. Полноценное перепланирование N4, предложение/решение N3, настройки уведомлений, гости/подарки/sharing остаются будущими срезами. Сохранение и удаление не вызывают Bot API.
- Русский интерфейс и CSS адаптации сохраняют 04/05/07, safe-area, native inputs, 1 колонку до desktop и 2 от 1024. Исправления среза 02 и отключение Vercel toolbar сохранены. Проверка фактического layout на 375/390/430/768/1024/1280 и physical iPhone не подменяется HTML/assertion.

## Проверки

Локальные tests используют actual handlers/services и PostgreSQL PGlite под fe_server. Дополнены: CSRF/owner/strict schema/version DELETE, возврат receipt/конфликт key, отсутствие повторных побочных эффектов, сохранение child history, отказ новых резервов/opt-in после удаления, реальный RSVP summary, snapshot normalization и rollback soft delete при искусственном сбое child update. Hosted smoke расширен реальными параллельными HTTP edit/delete и SQL reservation/HTTP delete, subscriber pending snapshot, отменой outbox, повтором после потерянного ответа, публичными/private/asset обложками, страницами, empty state. Fixtures ограничены текущим staging и удаляются в FK-порядке только для созданных синтетических owners, включая Storage originals/thumbnails.

## Ручная проверка iPhone

Выполнить в Telegram Mini App, Safari и установленной PWA, используя отдельное тестовое событие:

1. Открыть событие с обложкой/дополнительными полями. Ожидание: реальные значения, правильные дата/часы/зона, без фиктивных гостей.
2. Редактировать название/дату/время/место/описание; сохранить. Ожидание: сразу актуальная страница, затем правильная карточка после возврата и refresh.
3. Заменить обложку и сохранить, затем убрать и сохранить. Ожидание: обложка соответствует сохранённому состоянию на странице и в списке.
4. Открыть одно событие в двух вкладках Safari, изменить и сохранить в первой. Во второй не потерять ввод; при сохранении старой версии — понятный конфликт и явная загрузка актуальной версии с предупреждением о потере ввода.
5. «•••» → «Удалить событие». Ожидание: название/предупреждение и две кнопки. Нажать «Отмена»; событие остаётся и после refresh. Повторить отмену через Telegram BackButton.
6. Отключить сеть. Ожидание: удаление недоступно. Включить сеть и повторить confirmation. Подтвердить один раз; ожидание: «Удаляем…», нельзя отправить повторно/закрыть до ответа. После успеха — «Мои события», «Событие удалено», карточки нет; если последняя — empty state.
7. Вернуться по Back/старому адресу и открыть сохранённый edit-адрес, обновить; ожидание: «Событие недоступно», без данных и действий. Другая открытая вкладка при возврате тоже перечитывает данные (видимая management не позже очередной 15s проверки, edit 30s, при доступной сети).
8. Повторно открыть приложение и refresh списка: удалённое событие отсутствует. Открыть чужой приватный адрес другим Telegram-аккаунтом: недоступно.
9. В Safari открыть edit-форму, заполнить изменение, выйти через вторую вкладку, вернуться. Ожидание: вход; после входа тем же аккаунтом допустимый ввод восстановлен без отправки.
10. Проверить узкий экран, прокрутку/клавиатуру, нижнюю safe-area, русский текст, focus/VoiceOver labels. Если после искусственного обрыва запроса появилось «Проверить удаление», нажать её после подключения: один подтверждённый результат без дублей; не считать отсутствие сети подтверждением успеха.
