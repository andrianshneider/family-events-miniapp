Среда: существующий staging https://family-events-staging.vercel.app; ветка `infrastructure-foundation`. Main/Production не изменяются. Источники и чужие правки макетов сохранены.

Локальные отчёты 01–09 использованы как история реализации, а не доказательство новой физической проверки.

Уже реализованы: стабильный manifest id/start_url/scope `/`, standalone, app name/theme/apple metadata/иконки192/512/180; signed Mini App и OIDC с единым `app.users.telegram_user_id`; серверные cookie/CSRF/владение; реальные события/RSVP/Storage/wishlist/бронь; noindex/OG/Share и обработка soft delete. Основные экраны повторно проверяют сервер после visibility/pageshow/online, а формы защищают несохранённый ввод. Отдельного PWA-аккаунта нет. OIDC использует подтверждённый signed profile.id, не username/sub; проверяет signature/issuer/audience/expiry/state/nonce/PKCE.

Пробелы: инструкция установки была только для iPhone, без runtime platform/standalone/Mini App detection; нативный install prompt не использовался; отдельная maskable icon и безопасное поведение навигации без сети отсутствовали. CSS уже скрывал инструкцию в стандартном standalone, но не обрабатывал все runtime-контексты.

## Изменения

Глобальный PWA provider сохраняет deferred install prompt между клиентскими переходами. Установка вызывается только пользовательским нажатием и синхронно сохраняет user activation; отмена не считается установкой. appinstalled/standalone/fullscreen/iOS standalone/Mini App скрывают предложение. В Chrome/Edge/Android кнопка показывается только при реальном beforeinstallprompt; Safari iPhone/iPad получает инструкцию «На экран Домой», включая desktop-UA iPad. Неподдерживаемый браузер не получает ложного обещания установки.

Maskable512 использует существующее сердце/цвет проекта, контент внутри safe circle. Manifest сохраняет прежний id, чтобы не создавать вторую установленную идентичность, и явно запрещает предпочтение стороннего приложения.

Минимальный service worker кеширует только общий `/offline.html`. API/auth/writes/assets/media не перехватываются; навигация идёт network/no-store. Ошибка сети даёт общий русский экран с повтором исходного URL и автоматическим повтором при online. Персональные страницы, токены, события/ответы и картинки в CacheStorage не сохраняются. Worker обновляется без HTTP-кеша при старте/возврате; чистит только собственные старые offline-кеши, без принудительного перезапуска формы. Полная офлайн-запись не реализуется. В уже открытом приложении показывается общая информация о потере сети, существующие ошибки/повтор экранов сохранены.

БД, роли/RLS, ресурсы и scheduler не менялись; миграции не нужны. Новых Telegram-сообщений этот срез не отправляет. По срезу09 N3/N4 имеют реальные provider ACK, пользователь подтвердил N3/CTA; подтверждение получения N4/CTA отдельно ещё не получено.

## Ручная проверка: шаг → ожидаемый результат

Используйте одно событие «Проверка PWA — staging», один Telegram-аккаунт Organizer и два независимых приватных контекста Guest. Уведомления тестового события оставьте выключенными, чтобы эта проверка не создавала рассылку.

1. **Web:** откройте staging и войдите через Telegram. Создайте указанное событие, добавьте подарок с фото. → Событие и подарок сохранены; фото видно; refresh сохраняет результат.
2. **Установка desktop Chrome/Edge:** используйте кнопку приложения, если браузер её предложил, либо пункт установки в меню браузера. → Установлено Family Events с корректной иконкой; запуск открывает отдельное окно. Кнопка установки внутри него отсутствует. Нативное предложение может зависеть от времени/взаимодействий и предыдущей установки.
3. **iPhone Safari:** «Поделиться» → «На экран Домой», включите открытие как веб-приложение, если переключатель есть. Откройте иконку. → Отдельное приложение, правильное название/иконка, safe-area, нет повторного предложения установки. Если нужен вход, используйте тот же Telegram-аккаунт.
4. **Android Chrome:** установите доступным способом и откройте иконку. → Работает standalone; нет повторной установки. Если устройства нет, отметьте шаг непроверенным.
5. **Три контекста:** откройте «Мои события» в Telegram Mini App, Web и PWA. Измените описание события в одном контексте и вернитесь в другие. → Тот же набор событий и новая версия данных после восстановления/refresh. Отдельные cookie могут потребовать отдельного входа; аккаунт и БД остаются общими.
6. **Share и приглашение:** скопируйте ссылку, проверьте её в первом приватном браузере, сообщении Telegram и при навигации внутри PWA. Используйте native Share, отмените диалог и повторите. → Нужная Public Event без Organizer login; отмена не показывает ложный успех. Refresh `/e/{id}` и вложенного wishlist работает. ОС может открыть внешнюю ссылку в браузере вместо PWA — это допустимый fallback.
7. **Guest:** в первом приватном контексте ответьте «Буду», 2 взрослых/1 ребёнок, затем забронируйте подарок и обновите страницу. → Сохранён ответ и собственная бронь, можно изменить ответ и отменить свою бронь; регистрация не нужна.
8. **Второй Guest и Organizer:** откройте ссылку во втором независимом приватном контексте. → Подарок «Уже выбран», чужой ответ/имя/отмена недоступны. Organizer видит ответ/счётчики во всех трёх контекстах; Surprise скрывает имя выбравшего. После отмены первым гостем подарок снова свободен.
9. **Жизненный цикл/сеть:** закройте и повторно откройте PWA; уйдите в фон и вернитесь. Отключите сеть, после первого успешного открытия приложения обновите вложенную страницу, затем восстановите сеть. → Вход/данные восстанавливаются через сервер; offline не показывает персональный кеш и не подтверждает запись; повтор возвращает исходную страницу. Самый первый запуск без сети до установки worker может показать браузерную ошибку.
10. **Сессия/удаление:** выйдите из выбранного Organizer-контекста; Back/refresh не должны возвращать рабочий доступ. Войдите другим Telegram-аккаунтом при наличии: данные предыдущего недоступны. Удалите только тестовое событие после остальных проверок. → Активная сессия отозвана; другие независимые сессии действуют по текущей модели. Тестовое событие исчезает; старое приглашение и wishlist недоступны.

Для входа в PWA после подтверждения в Telegram вручную вернитесь, если ОС не переключила приложения. Ожидается успешное завершение входа в исходном контексте. Если callback открыл другой браузер и PWA не восстановила вход, зафиксируйте это как ошибку, а не как подтверждённый успех.

## Ограничения доказательств

Браузерный extension bridge не запускается; native Chrome занят пользователем и не использован для проверки его рабочих вкладок. Реальная установка/standalone, iPhone/Android/PWA OIDC и системный Share пока не подтверждены. Эти шаги нельзя заменить HTTP-smoke или сменой user-agent. Автоматическое переключение Telegram→Safari/PWA и захват внешних ссылок установленным приложением не гарантируются ОС. Полная офлайн-работа, push и новые бизнес-функции вне этого среза.

## Итог staging-проверки

`pwa-smoke.ts` завершился exit0: manifest MIME/id/scope/standalone, все реальные размеры иконок, worker scope/no-store и offline document; создание Event через API; настоящий Storage upload/complete; Gift; canonical Share URL; анонимный SSR Public Event и вложенных wishlist/detail; yes RSVP и refresh; бронь/own refresh, занятость и запрет чужой отмены для независимого Guest; Surprise projection; summary из всех трёх независимых cookie-сессий одного synthetic ID; изменение RSVP без дубля; отмена брони; logout только одной сессии; soft delete закрывает приглашение и wishlist. Синтетические учётные записи не имели подписок: бот не вызывался, scheduler не приостанавливался.

Первый запуск выявил неверное тестовое ожидание заголовка Gift Detail; исправлено. Следующий прошёл бизнес-сценарий, но очистка пропустила зависимые RSVP. Порядок очистки исправлен, добавлен приватный журнал точных идентификаторов текущего запуска для восстановления при сбое; финальный запуск полностью очистил свои фикстуры и журнал. Помеченные остатки предыдущего запуска (два synthetic Organizer и связанный тестовый Guest) удалены после проверки меток. Одну неиспользованную анонимную сессию предыдущего сбоя невозможно однозначно отличить от других анонимных гостей; непроверенные сессии сохранены, без массового удаления. Это не активный RSVP/бронь и не изменение реального гостя.

Инфраструктурный readback: 22 app tables; anon Guest verifier EXECUTE=false, worker=true; существующий minute scheduler active=true, последний HTTP200/timed_out=false. Изменений схемы, разрешений или инфраструктурных ресурсов нет.

Физическая установка, standalone запуск, реальный OIDC в установленной PWA, сравнение одного реального Organizer в трёх платформах, системный Share и iPhone/Android safe-area остаются ручной приёмкой по шагам выше. Пользователю направлен запрос на такую проверку; результат пока не получен. Срез реализован и прошёл доступную автоматическую проверку, но полная физическая приёмка не заявляется завершённой.

Технические источники установки: [официальные критерии Chrome](https://web.dev/articles/install-criteria), [руководство Next.js PWA](https://nextjs.org/docs/app/guides/progressive-web-apps). Отсутствие install prompt не трактуется как доказательство ошибки manifest: браузер применяет собственные критерии и условия показа.
