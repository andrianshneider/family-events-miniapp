Продукт: Family Events OS
Версия: MVP
Основная платформа: Telegram Mini App

1. Концепция продукта
Family Events OS — сервис для организации семейных и частных мероприятий, который позволяет организатору создать событие, собрать в одном месте всю необходимую информацию, пригласить гостей одной ссылкой, получить подтверждения участия и организовать wishlist подарков.
Основная идея MVP:
Создать событие за несколько минут → отправить одну ссылку → гость без регистрации получает всю информацию, отвечает на приглашение и при необходимости выбирает подарок.
Продукт должен одинаково работать:
* внутри Telegram как Mini App;
* по обычной ссылке в мобильном/desktop-браузере;
* как установленное PWA-приложение.
Используется одна кодовая база и одна backend-инфраструктура.
2. Цель MVP
MVP должен проверить четыре основные продуктовые гипотезы.
H1. Creation
Пользователям достаточно полезен сервис, чтобы создавать в нем реальные мероприятия.
H2. Distribution
Организаторы готовы использовать ссылку Family Events как основное приглашение или дополнение к приглашению.
H3. Guest utility
Гости готовы взаимодействовать со страницей события: отвечать RSVP и пользоваться wishlist.
H4. Viral loop
Часть гостей после знакомства с Family Events самостоятельно становится организаторами новых мероприятий.
Ключевая петля роста:
Organizer → Event → Guests → Guest becomes Organizer → New Event → New Guests
3. Scope MVP
В MVP входят строго семь продуктовых функций:
1. Event Creation
2. Event Page
3. Share / Invitation
4. RSVP
5. Wishlist
6. Gift Reservation
7. Telegram Notifications
Дополнительно PWA, авторизация и аналитика являются инфраструктурой MVP, а не самостоятельными пользовательскими функциями.
4. Что НЕ входит в MVP
До завершения Alpha не разрабатываем:
* встроенный групповой чат;
* поиск ресторанов;
* бронирование ресторанов;
* поиск фотографов;
* поиск аниматоров;
* marketplace подрядчиков;
* платежи;
* сбор денег с гостей;
* совместную покупку подарков;
* gift cards;
* affiliate commerce;
* AI event planner;
* фотоальбом;
* семейный календарь;
* социальную сеть;
* друзей/подписчиков;
* несколько организаторов одного события;
* сложные пользовательские профили;
* email-уведомления;
* SMS;
* browser Web Push;
* native iOS App;
* native Android App;
* App Store / Google Play;
* сложную систему прав доступа;
* публичный поиск мероприятий.
Правило scope:
До выхода Alpha новая пользовательская функция добавляется только в случае, если одновременно удаляется функция сопоставимой сложности.
5. Типы пользователей
5.1 Organizer
Авторизованный пользователь, создающий мероприятие.
Organizer может:
* создавать события;
* редактировать свои события;
* удалять свои события;
* управлять wishlist;
* видеть RSVP;
* видеть количество гостей;
* создавать и копировать invitation link;
* включать Telegram-уведомления;
* получать уведомления об RSVP.
В MVP у события только один Organizer.
5.2 Guest
Человек, получивший ссылку на мероприятие.
Для Guest не требуется регистрация.
Guest может:
* открыть событие;
* посмотреть всю информацию;
* ответить RSVP;
* изменить свой RSVP;
* посмотреть wishlist;
* забронировать подарок;
* отменить свою бронь;
* включить Telegram-уведомления.
Guest не может:
* редактировать событие;
* видеть персональные данные остальных гостей;
* управлять wishlist;
* видеть, кто забронировал подарок.
6. Основные продуктовые принципы
6.1 Guest без регистрации
Получение приглашения не должно приводить к экрану:
Зарегистрироваться → email → пароль → подтверждение → вход.
Правильный flow:
Ссылка → Event Page → RSVP.
6.2 One link
У каждого события существует один постоянный публичный URL:
familyevents.app/e/{public_id}
Он работает:
* в Telegram;
* WhatsApp;
* iMessage;
* email;
* SMS;
* браузере;
* PWA.
Ссылка не должна зависеть от Telegram.
6.3 Unlisted by default
Событие не является публично индексируемой страницей.
Доступ получает любой человек, знающий ссылку.
У мероприятия должен использоваться непредсказуемый public_id.
6.4 Mobile first
Главный сценарий использования — смартфон.
Первичная разработка интерфейсов:
375–430 px
с последующей адаптацией под tablet и desktop.
6.5 Minimum friction
При каждом решении выбираем вариант с меньшим количеством действий гостя.
7. Авторизация
7.1 Telegram Mini App
При открытии Mini App пользователь идентифицируется через Telegram.
Если пользователь еще не существует:
создается user.
Если существует:
открывается существующий аккаунт.
Дополнительная регистрационная форма отсутствует.
7.2 Browser / PWA
На экране Organizer используется:
«Войти через Telegram»
После входа пользователь получает доступ к тем же событиям, что и в Mini App.
Telegram-аккаунт является основной идентичностью Organizer.
7.3 Guest
Авторизация не требуется.
При первом действии, требующем идентификации:
* RSVP;
* бронирование подарка;
создается Guest Session.
Для Telegram-пользователя она может связываться с Telegram ID.
Для анонимного web-пользователя создается локальный безопасный идентификатор.

20. Идентификация Guest
Если Guest находится внутри Telegram:
используется Telegram identity.
Если Guest работает анонимно через browser:
создается безопасная Guest Session.
Она позволяет на том же устройстве:
* увидеть свой RSVP;
* изменить RSVP;
* увидеть свои gift reservations;
* отменить свою reservation.
Ограничение MVP
Если анонимный Guest:
1. открыл событие в Safari;
2. отправил RSVP;
3. затем открыл ту же ссылку на другом устройстве;
Family Events может не определить, что это тот же человек.
Это допустимое ограничение MVP.
После подключения Telegram Notifications проблема исчезает благодаря привязке к Telegram identity.

27. Gift Reservation
При бронировании выполняется серверная проверка.
Одновременно один Gift может иметь максимум одну активную Reservation.
Если два пользователя пытаются забронировать его одновременно:
первый успешный запрос получает подарок.
Второй получает:
Этот подарок только что выбрал другой гость.
Кнопка:
Выбрать другой
Это правило обязательно обеспечивается backend/database, а не только интерфейсом.

49. Security Requirements
Обязательно:
* Telegram authentication валидируется server-side;
* Organizer имеет доступ только к своим Event;
* Guest не может получить Guest List через API;
* public ID невозможно предсказать перебором последовательных чисел;
* Gift reservation защищена от simultaneous booking;
* Surprise reservation identity не передается Organizer через frontend API;
* пользовательский HTML не исполняется;
* ссылки проходят validation;
* изображения ограничены по типу и размеру;
* destructive actions требуют confirmation.
50. Performance
Цель для Public Event Page:
* максимально быстрый first load;
* оптимизированные изображения;
* минимальный JS, необходимый для initial render;
* usable на обычном мобильном интернете.
Public page является критичной для конверсии и должна иметь более высокий приоритет производительности, чем Organizer dashboard.

55. Acceptance Criteria — Event Creation
Функция принимается, если:
1. Авторизованный Organizer может создать Event.
2. Без Title Event создать невозможно.
3. Без Date Event создать невозможно.
4. После создания генерируется публичная ссылка.
5. Ссылка открывается без авторизации.
6. Organizer сразу видит Event в «Мои события».
7. Event можно редактировать.
8. Event можно удалить.
9. Данные после refresh сохраняются.
56. Acceptance Criteria — Event Page
Функция принимается, если:
1. Public Event доступен без регистрации.
2. Показываются только заполненные Organizer поля.
3. Дата отображается корректно.
4. Адрес можно использовать для построения маршрута.
5. Invitation link имеет корректный social preview.
6. Event не индексируется поисковиками.
7. Deleted Event недоступен.
8. Страница адаптирована для телефона и desktop.
57. Acceptance Criteria — Share
Функция принимается, если:
1. Organizer может скопировать public URL.
2. Organizer может вызвать Share action.
3. URL работает вне Telegram.
4. URL работает внутри Telegram.
5. Одна и та же ссылка открывает одно и то же Event.
58. Acceptance Criteria — RSVP
Функция принимается, если:
1. Guest может ответить без регистрации.
2. Поддерживаются Yes / No / Maybe.
3. Для Yes можно указать взрослых и детей.
4. Guest может добавить комментарий.
5. RSVP появляется у Organizer.
6. Guest на том же устройстве может изменить ответ.
7. Изменение не создает второй RSVP той же Guest Session.
8. Organizer видит корректные totals.
59. Acceptance Criteria — Wishlist
Функция принимается, если:
1. Organizer может создать Gift.
2. Gift может существовать без URL.
3. Gift может существовать без цены.
4. Guest видит wishlist без авторизации.
5. Organizer может редактировать Gift.
6. Organizer может удалить Gift.
7. Wishlist может работать в Surprise mode.
60. Acceptance Criteria — Gift Reservation
Функция принимается, если:
1. Guest может выбрать свободный Gift.
2. После reservation остальные гости видят его как занятый.
3. Один Gift невозможно одновременно забронировать двум Guest.
4. Guest может отменить собственный выбор.
5. Guest не может отменить reservation другого Guest.
6. Organizer в Surprise mode не получает имя reserving Guest.
7. Refresh страницы не теряет состояние.
61. Acceptance Criteria — Notifications
Функция принимается, если:
1. Telegram message не отправляется без permission.
2. Organizer получает новый RSVP.
3. Organizer получает изменение RSVP.
4. Guest может opt-in после RSVP.
5. Guest получает уведомление при значимом изменении Event.
6. Guest со статусом Yes получает reminder.
7. Guest со статусом No reminder не получает.
8. Один trigger не приводит к duplicate notification.
62. Acceptance Criteria — Cross-platform
Функция принимается, если один и тот же Organizer:
1. открывает Mini App;
2. создает Event;
3. затем входит через browser;
4. видит то же Event;
5. устанавливает PWA;
6. видит в PWA те же данные.
Никакой отдельной базы или отдельного аккаунта для каждой платформы нет.
63. Critical QA Scenarios
Перед Alpha обязательно проверить:
RSVP concurrency
Несколько гостей одновременно отправляют RSVP.
Gift concurrency
Два разных пользователя одновременно нажимают:
Выбрать этот подарок
Event edit
Organizer изменяет дату после появления RSVP.
Event deletion
Organizer удаляет Event с существующими RSVP и reservations.
Browser refresh
Guest делает RSVP → закрывает страницу → снова открывает ссылку.
Telegram/browser transition
Guest открывает web invitation → подключает Telegram notifications → открывает Event через Telegram.
Timezones
Событие создается в одной timezone и открывается гостем из другой.

65. North Star на этапе MVP
Основной показатель продукта:
Active Events
Количество реальных мероприятий, для которых одновременно:
* создан Event;
* invitation link открыт хотя бы одним Guest;
* получен хотя бы один RSVP.
Это лучше простой метрики registered users, поскольку показывает фактическое использование продукта.
66. Definition of Done — MVP
MVP считается готовым к закрытому Alpha-тестированию, когда реальный пользователь без помощи разработчика способен пройти полностью:
Organizer Flow
Telegram → Family Events → Create Event → Add information → Add Gifts → Share Link → Receive RSVP
и:
Guest Flow
Invitation Link → Event Page → RSVP → Wishlist → Reserve Gift → Enable Telegram Reminder
После этого Organizer:
получает RSVP → видит Guest List → получает уведомление
а Guest:
получает reminder перед мероприятием.
Все это должно работать на production-like environment с одной базой данных для Mini App, Browser и PWA.
67. Главный UX-тест MVP
Новый Organizer должен быть способен без инструкции:
создать первое мероприятие и получить ссылку для отправки гостям.
Новый Guest должен быть способен без инструкции:
открыть ссылку и ответить, придет ли он.
Если пользователь вынужден спрашивать, как выполнить эти действия, UX считается требующим доработки.
