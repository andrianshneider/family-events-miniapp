Family Events OS
Technical Specification v1.0 + схема БД
Дата: 10.10.2026. Базовый продуктовый документ: PRD MVP v1.0 от 01.10.2026.
Назначение: контракт реализации MVP для Next.js + TypeScript, Supabase PostgreSQL + Storage, Telegram Mini App / Bot / OIDC, Web и PWA.
Документ состоит из четырёх частей. Технические решения v1.0 ниже задают реализацию требований PRD; значения TTL, лимиты загрузки и правила слияния идентичностей являются проектными решениями этой спецификации.
Приоритет источников: PRD v1.0 → инструкция разработки → ранний пошаговый план. Поэтому N3 (изменение события) и N4 (напоминание) входят в MVP, хотя ранний план откладывал напоминания.

1. Database schema
1.1 Архитектура и соглашения
Одна БД для Mini App, Web и PWA. Все клиентские операции идут через Next.js API/BFF; прямой доступ браузера к бизнес-таблицам закрыт. Серверный DAL проверяет principal, владение и состояние сущности перед каждым запросом. Service-role Supabase доступен только серверу и worker; он обходит RLS, поэтому RLS не заменяет эти проверки.
Бизнес-таблицы находятся в непубличной схеме app, не включённой в exposed schemas PostgREST. Дополнительно включён RLS без клиентских политик и отозваны grants у anon/authenticated. Сервер использует отдельный ограниченный DB role через подключение PostgreSQL; worker имеет доступ только к своим функциям. RPC с SECURITY DEFINER имеет фиксированный search_path и не выдаётся клиентским ролям.
Общие типы: PK uuid DEFAULT gen_random_uuid(); timestamps timestamptz; текст Unicode. NN означает NOT NULL. Если NULL не указан, поле NN. created_at DEFAULT now(); updated_at обновляет trigger. FK по умолчанию ON DELETE RESTRICT. Soft delete не запускает физический CASCADE.
Дата и локальные часы события хранятся отдельно с IANA timezone. UTC instant вычисляется сервером и сохраняется для сортировки и планирования. Цена numeric(12,2); float для денег запрещён. Telegram ID bigint; в JSON передаётся строкой.
Публичный public_id: 128 бит криптографической случайности, base64url, UNIQUE; не UUID внутреннего события и не порядковый номер. ID неизменяемый. События unlisted, доступ по ссылке; ссылка может быть переслана любым получателем и не является персональным приглашением.
1.2 Схема связей
users 1 → N organizer_sessions
users 1 → N events (единственный organizer)
users 1 → 0..1 guest_identities (Telegram-привязка)
guest_identities 1 → N guest_sessions
events 1 → 1 wishlists → N gifts → N gift_reservations (история; максимум одна active на gift)
events 1 → N rsvps ← N : 1 guest_identities
guest_identities 1 → N gift_reservations
users 1 → 0..1 telegram_channels
events + users → notification_subscriptions → notifications
events 1 → N event_changes
media_assets ← events.cover_asset_id / gifts.image_asset_id
analytics_events → events / guest_identities / users (nullable)
Одно RSVP относится к одному домохозяйству/ответу гостя, а не к каждому взрослому или ребёнку отдельно. RSVP и бронь используют guest_identity_id, а не session_id: обновление сессии не создаёт дубликаты.
1.3 users, organizer_sessions
users — подтверждённая Telegram-идентичность.
Поля: id uuid PK; telegram_user_id bigint UNIQUE CHECK > 0; display_name text CHECK length 1..128; username text NULL; avatar_url text NULL; locale text DEFAULT 'ru'; origin_event_id uuid NULL FK events; created_at; updated_at.
username не уникальный идентификатор и не основание для объединения аккаунтов. origin_event_id записывается один раз при подтверждённой конверсии Guest → Organizer.
organizer_sessions — серверные сессии Organizer.
Поля: id uuid PK; user_id uuid FK users; token_hash bytea UNIQUE CHECK octet_length=32; created_at; last_seen_at timestamptz; expires_at timestamptz; revoked_at timestamptz NULL.
CHECK expires_at > created_at. Индекс (user_id, expires_at). В БД только SHA-256 hash случайного 256-bit токена; исходный токен хранится в HttpOnly cookie. Absolute TTL 30 дней; logout отзывает текущую сессию.
1.4 events, event_changes
events — мероприятие.
Поля: id uuid PK; organizer_id uuid FK users; public_id text UNIQUE; title text CHECK char_length(trim(title)) BETWEEN 3 AND 80; event_type text CHECK IN ('birthday','kids_birthday','anniversary','party','family','other'); event_date date; start_time time NULL; end_time time NULL; timezone text; starts_at timestamptz NULL; ends_at timestamptz NULL; effective_at timestamptz; venue_name text NULL CHECK length ≤200; address text NULL CHECK length ≤500; latitude numeric(9,6) NULL; longitude numeric(9,6) NULL; directions text NULL CHECK length ≤500; description text NULL CHECK length ≤1000; dress_code text NULL CHECK length ≤300; cover_asset_id uuid NULL FK media_assets; version integer DEFAULT 1 CHECK >0; deleted_at timestamptz NULL; created_at; updated_at.
CHECK: end_time IS NULL OR (start_time IS NOT NULL AND end_time > start_time). Ночное событие через полночь в v1.0 не поддерживается. Координаты либо обе NULL, либо обе заданы; latitude −90..90, longitude −180..180. timezone проверяется по IANA на сервере. При указанном времени starts_at обязателен; иначе starts_at/ends_at NULL, effective_at = локальная полночь event_date, переведённая в UTC.
При создании event_date не раньше текущего дня в timezone события — серверная проверка, не CHECK с now(). Редактирование уже прошедшего события не блокируется этой проверкой. Неоднозначное или несуществующее локальное время при DST требует уточнения в UI; запрещено молча менять час.
upcoming/past вычисляются относительно effective_at; deleted по deleted_at. Отдельное изменяемое поле status и draft отсутствуют. Напоминания используют правило из 1.9.
Индексы: UNIQUE(public_id); (organizer_id,event_date) WHERE deleted_at IS NULL; (effective_at) WHERE deleted_at IS NULL.
Создание events + wishlists выполняется одной транзакцией. UPDATE принимает expected_version, повышает version; несовпадение → 409 VERSION_CONFLICT.
event_changes — снимок значимых изменений для подтверждения рассылки.
Поля: id uuid PK; event_id uuid FK events; event_version integer; actor_user_id uuid FK users; changes jsonb; created_at; notify_decision text DEFAULT 'pending' CHECK IN ('pending','send','skip'); decided_at timestamptz NULL. UNIQUE(event_id,event_version).
changes содержит только before/after даты, времени, timezone, места и адреса. Сохранение события не отправляет N3 автоматически. Отдельное подтверждение send создаёт одну рассылку на этот change_id. При отсутствии подписчиков решение skip допустимо сразу.
1.5 guest_identities, guest_sessions, auth_handoffs
guest_identities — долговечный субъект гостя, общий для разных мероприятий.
Поля: id uuid PK; linked_user_id uuid NULL UNIQUE FK users; display_name text NULL CHECK length 2..60; origin_event_id uuid NULL FK events; merged_into_id uuid NULL FK guest_identities; created_at; updated_at.
CHECK merged_into_id IS NULL OR merged_into_id <> id. Отсутствие циклов merge контролирует функция привязки. Для каждого подтверждённого Telegram user существует максимум одна canonical guest identity. display_name — удобный default, а актуальное имя RSVP хранится в rsvps.
guest_sessions — доступ устройства к гостевому субъекту.
Поля: id uuid PK; guest_identity_id uuid FK guest_identities; token_hash bytea UNIQUE CHECK octet_length=32; created_at; last_seen_at; expires_at; revoked_at NULL. CHECK expires_at > created_at. Индекс (guest_identity_id,expires_at). Absolute TTL 180 дней; отсутствие cookie означает нового анонимного гостя. UUID identity нельзя использовать как credential.
auth_handoffs — одноразовая безопасная привязка browser → Telegram.
Поля: id uuid PK; token_hash bytea UNIQUE; guest_identity_id uuid FK guest_identities; event_id uuid FK events; expires_at timestamptz; consumed_at timestamptz NULL; confirmed_user_id uuid NULL FK users; created_at. TTL 10 минут. CHECK expires_at > created_at.
Дополнительно server-side OIDC transaction store (Redis либо таблица auth_transactions): id uuid PK; state_hash bytea UNIQUE; nonce_hash bytea; pkce_verifier_ciphertext bytea; guest_session_id uuid NULL FK guest_sessions; return_path text; expires_at timestamptz; consumed_at NULL; created_at. TTL 10 минут, одноразовое consume. Redirect только на allowlist собственных relative paths. Секрет verifier шифруется серверным ключом.
1.6 rsvps
Поля: id uuid PK; event_id uuid FK events; guest_identity_id uuid FK guest_identities; guest_name text CHECK char_length(trim(guest_name)) BETWEEN 2 AND 60; status text CHECK IN ('yes','no','maybe'); adults_count smallint; children_count smallint; comment text NULL CHECK length ≤300; version integer DEFAULT 1 CHECK >0; created_at; updated_at.
UNIQUE(event_id,guest_identity_id). CHECK: (status='no' AND adults_count=0 AND children_count=0) OR (status IN ('yes','maybe') AND adults_count BETWEEN 1 AND 20 AND children_count BETWEEN 0 AND 20).
Индексы: (event_id,status); (guest_identity_id,event_id). PUT выполняет atomic UPSERT; повтор сохранения неизменного payload не увеличивает version и не создаёт N2.
Dashboard: yes/no/maybe — число ответов; adults/children — SUM только для yes. maybe totals можно показывать отдельно с явной подписью. Число приглашённых неизвестно при единой ссылке; нельзя выдавать opens за приглашённых. Неответившие гости не создаются автоматически из посещений.
1.7 wishlists, gifts, gift_reservations
wishlists: id uuid PK; event_id uuid UNIQUE FK events; hide_reserver_identity boolean DEFAULT true; created_at; updated_at.
gifts: id uuid PK; wishlist_id uuid FK wishlists; title text CHECK length(trim(title)) 2..120; external_url text NULL; amount numeric(12,2) NULL; currency char(3) NULL; comment text NULL CHECK length ≤300; image_asset_id uuid NULL FK media_assets; sort_order integer DEFAULT 0; version integer DEFAULT 1 CHECK >0; deleted_at timestamptz NULL; created_at; updated_at.
CHECK (amount IS NULL AND currency IS NULL) OR (amount>0 AND currency IN ('RUB','EUR','USD')). HTTP/HTTPS URL валидируется сервером; javascript/data/file запрещены. В v1.0 сервер не загружает данные по внешнему URL. Индекс (wishlist_id,sort_order,created_at) WHERE deleted_at IS NULL.
gift_reservations: id uuid PK; gift_id uuid FK gifts; guest_identity_id uuid FK guest_identities; status text DEFAULT 'active' CHECK IN ('active','cancelled'); reserved_at timestamptz DEFAULT now(); cancelled_at timestamptz NULL; cancel_reason text NULL CHECK IN ('guest_cancelled','gift_deleted','event_deleted','identity_merge'); version integer DEFAULT 1.
CHECK (status='active' AND cancelled_at IS NULL AND cancel_reason IS NULL) OR (status='cancelled' AND cancelled_at IS NOT NULL AND cancel_reason IS NOT NULL).
Ключевой constraint: CREATE UNIQUE INDEX uq_gift_active_reservation ON app.gift_reservations(gift_id) WHERE status='active';
Индекс (guest_identity_id,reserved_at) WHERE status='active'. Gift availability вычисляется из активной брони, отдельный изменяемый gifts.status отсутствует. Один гость может выбрать несколько разных подарков.
POST reserve: транзакция блокирует event, затем gift; проверяет отсутствие deleted_at; вставляет reservation. UNIQUE violation для другого гостя → 409 GIFT_ALREADY_RESERVED. Если активная бронь уже принадлежит текущему субъекту, возвращается существующая бронь без дубля. Отмена меняет status только при совпадении guest_identity_id.
DELETE gift soft-deletes gift и отменяет active reservation в той же транзакции. Если подарок занят, требуется confirm_reserved=true после отдельного UI-confirmation; без него 409 CONFIRM_RESERVED_GIFT_DELETE. Organizer не получает identity даже при этом подтверждении.
1.8 media_assets
Поля: id uuid PK; owner_user_id uuid FK users; storage_path text UNIQUE; mime_type text CHECK IN ('image/jpeg','image/png','image/webp'); byte_size integer CHECK BETWEEN 1 AND 10485760; width integer CHECK >0; height integer CHECK >0; state text CHECK IN ('pending','ready','deleted'); created_at; deleted_at NULL.
Лимит v1.0: 10 MiB, до 20 мегапикселей. MIME определяется по содержимому, а не расширению. Сервер перекодирует изображение, удаляет EXIF, проверяет размер; SVG/HTML не принимаются. Разрешены только ready assets владельца события; это cross-table проверка DAL/DB function, а не обычный CHECK.
Storage private. Public DTO отдаёт короткоживущий signed URL либо media-proxy для конкретного активного события. OG-cover доступна crawler без login через разрешённый proxy с непредсказуемым event public_id. После soft delete media-proxy закрывается; копии и previews на внешних платформах не могут быть гарантированно удалены. Незакреплённые pending assets удаляет cleanup job через 24 часа.
1.9 telegram_channels, notification_subscriptions, notifications
telegram_channels: user_id uuid PK FK users; chat_id bigint UNIQUE; permission_granted_at timestamptz NULL; permission_source text NULL CHECK IN ('mini_app','oidc','bot_start'); delivery_state text DEFAULT 'unknown' CHECK IN ('unknown','ready','blocked'); last_verified_at NULL; updated_at.
Авторизация сама по себе не разрешает рассылку. Delivery возможна только при явном opt-in и подтверждённом доступном канале бота.
notification_subscriptions: id uuid PK; event_id uuid FK events; user_id uuid FK users; role text CHECK IN ('organizer','guest'); guest_identity_id uuid NULL FK guest_identities; enabled boolean DEFAULT false; consented_at timestamptz NULL; revoked_at timestamptz NULL; created_at; updated_at.
UNIQUE(event_id,user_id,role). CHECK: organizer → guest_identity_id NULL; guest → guest_identity_id NOT NULL. enabled=true требует consented_at и revoked_at NULL. Для organizer user_id должен совпадать с events.organizer_id; для guest — с linked_user_id canonical identity. Проверяются сервером и DB function.
notifications — transactional outbox и очередь доставки.
Поля: id uuid PK; subscription_id uuid FK notification_subscriptions; type text CHECK IN ('rsvp_new','rsvp_changed','event_changed','reminder_24h'); trigger_key text; payload jsonb; scheduled_at timestamptz; status text DEFAULT 'pending' CHECK IN ('pending','processing','sent','failed','cancelled'); attempts integer DEFAULT 0 CHECK ≥0; next_attempt_at timestamptz; locked_until timestamptz NULL; sent_at timestamptz NULL; provider_message_id bigint NULL; last_error_code text NULL; created_at.
UNIQUE(subscription_id,type,trigger_key). Индекс (next_attempt_at,scheduled_at) WHERE status='pending'. payload содержит только необходимый текст уведомления; gift identity в outbox не включается.
N1 trigger_key=rsvp:{id}:v1; N2=rsvp:{id}:v{version}; N3=change:{change_id}; N4=event:{id}:schedule:{version}. RSVP + outbox пишутся одной транзакцией; API не ждёт sendMessage.
Worker каждые 60 секунд выбирает due rows через FOR UPDATE SKIP LOCKED, фиксирует lease, отправляет Bot API, помечает результат. Retry до 5 попыток с backoff и jitter; 429 учитывает retry_after, 403 блокирует канал. Истёкшие leases возвращаются в очередь.
Перед отправкой повторно проверяются opt-in, состояние event, актуальная версия расписания и RSVP. N4 допускает yes/maybe, исключает no; для maybe текст не утверждает участие. Без RSVP reminder не создаётся. Для события без start_time проектное правило v1.0: напомнить в 09:00 timezone события за день до event_date, без выдуманного времени начала. Если момент напоминания уже прошёл, немедленное напоминание не отправляется.
Изменение даты/времени отменяет несданные старые reminders и планирует новые вне зависимости от решения send/skip по N3. Отказ от уведомлений отменяет pending jobs. Удаление event отменяет очередь.
Гарантия: один outbox job на trigger; Telegram Bot API не даёт общей exactly-once гарантии. Если Telegram принял сообщение, а worker потерял ответ, повторная попытка может создать дубль. Это ограничение фиксируется в QA и мониторинге; нельзя обещать абсолютное отсутствие дублей.
1.10 analytics_events и системные гарантии
analytics_events: id uuid PK; name text; event_id uuid NULL FK events; guest_identity_id uuid NULL FK guest_identities; user_id uuid NULL FK users; anonymous_visitor_id uuid NULL; client_event_id uuid NULL UNIQUE; properties jsonb DEFAULT '{}'; occurred_at timestamptz; received_at timestamptz DEFAULT now(). Индексы (name,occurred_at), (event_id,occurred_at).
Allowlist событий из PRD: user_authenticated, event_creation_started, event_created, event_edited, event_shared, event_opened, rsvp_started, rsvp_submitted, rsvp_changed, wishlist_opened, gift_created, gift_reserved, gift_unreserved, notification_opt_in_started, notification_opt_in_completed, guest_became_organizer.
Business events создаёт сервер после commit; views/shares передаёт клиент. Никаких имён, комментариев, Telegram ID, токенов и полного URL приглашения в analytics/logs. anonymous_visitor_id — случайный идентификатор, не credential гостя. Боты OG исключаются из visitor counts. Согласие/retention аналитики оформляются перед публичным запуском.
Guest → Organizer фиксируется при создании первого собственного события после гостевого взаимодействия, один раз на user; origin_event_id first-touch не перезаписывается. Между устройствами учитываются только доказанно связанные идентичности; точное число уникальных анонимных людей недостижимо.
Soft delete event атомарно: deleted_at, отмена active reservations, disabled subscriptions, cancel pending notifications. RSVP остаются во внутренней БД, но недоступны API. Проектный retention: purge удалённых events с зависимостями через 30 дней; outbox payload 30 дней; auth_handoffs после истечения удаляются ежедневно. Analytics до 90 дней, затем только агрегаты. Физический purge выполняется явно в FK-порядке, с очисткой Storage; origin_event_id/analytics event_id обнуляются.
Единый порядок блокировок: canonical identities при merge → event → wishlist/gift → RSVP/reservation → subscriptions/outbox. Все мутации дочерних объектов проверяют и блокируют event; удаление события не может оставить новую активную бронь. В миграциях обязателен FK индекс на часто используемых связях.
Идемпотентность: POST create и команды рассылки принимают Idempotency-Key. Таблица api_idempotency: id uuid PK; principal_key text; route text; key text; request_hash bytea; response_status integer NULL; response_body jsonb NULL; expires_at timestamptz; created_at. UNIQUE(principal_key,route,key); TTL 24 часа. Повтор с другим payload → 409. Запись ключа и результат мутации согласуются транзакционно; незавершённый повтор получает 409 REQUEST_IN_PROGRESS.
2. Authorization model
2.1 Telegram Organizer
Mini App: клиент отправляет raw Telegram.WebApp.initData в POST /api/auth/telegram/mini-app. Сервер валидирует подпись по официальному алгоритму Telegram и auth_date; допустимый возраст v1.0 — 5 минут. initDataUnsafe не доверяется. Секрет бота хранится только на сервере. После валидации Telegram user ID приводит к UPSERT users и выдаче organizer cookie. Fresh initData можно получить повторным запуском Mini App.
Web/PWA: GET /api/auth/telegram/start → Telegram OIDC Authorization Code + PKCE → GET /api/auth/telegram/callback. Проверяются state, одноразовость транзакции, nonce при использовании, JWT signature через JWKS, iss, aud, exp. Сервер связывает проверенный Telegram subject с тем же telegram_user_id; если provider subject нельзя надёжно сопоставить с ID Mini App, вход блокируется до подтверждённого mapping, а не создаёт отдельный аккаунт.
Cookie __Host-fe_org: Secure, HttpOnly, SameSite=Lax, Path=/, без Domain. При входе токен обновляется; logout отзывает. Любая мутация проверяет Origin/CSRF token; callback защищён state. Redirect URIs и origins регистрируются в BotFather. Bot webhook проверяет secret token и дедуплицирует update_id.
Источники протоколов: https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app и https://core.telegram.org/bots/telegram-login
Один Telegram-аккаунт → один users.id во всех клиентах. Наличие user не делает его владельцем всех событий: Organizer роль вычисляется через events.organizer_id.
2.2 Anonymous Guest Session
GET публичного события не создаёт авторизацию. При первом RSVP/reservation POST /api/guest/session создаёт guest_identity и session; cookie __Host-fe_guest имеет Secure, HttpOnly, SameSite=Lax, Path=/, TTL 180 дней. Имя обязательно для RSVP/первой брони, но создание session не требует имени.
Principal Guest разрешает доступ только к собственным RSVP/reservations по canonical identity. event public_id даёт чтение sanitized Event/Wishlist DTO, но не право изменять произвольные ответы. Сервер выводит guest_identity_id из cookie; никогда не принимает его как доказательство владения из body.
Если Telegram identity уже подтверждена, guest context использует canonical linked identity без дополнительной регистрации. Гость остаётся способен взаимодействовать анонимно в браузере. Очистка cookie или другое устройство до привязки означает новую identity; восстановление по имени запрещено.
2.3 Привязка гостя к Telegram и конфликты
После opt-in браузер получает одноразовый handoff и открывает Telegram deep link. Handoff не содержит raw cookie, session token или Telegram ID. Подтверждённый bot /start либо проверенное Mini App initData связывает token с Telegram user. Исходный browser session получает статус только своим credential; новый guest token выдаётся после завершения. Подтверждение consume выполняется атомарно, после TTL token недействителен.
Подписка enabled становится true только после явного согласия и готового канала, затем Guest доступен с подтверждённым Telegram на других устройствах. Просто открыть bot или пройти login недостаточно для неявной подписки на все события.
Merge в одной транзакции блокирует обе identities в стабильном порядке. Если canonical identity ещё нет — linked_user_id добавляется текущей. Если она есть — anonymous identity вливается в canonical; сессии и брони переносятся, источник помечается merged_into_id.
Если обе identities имеют RSVP одного event, UI показывает конфликт и предлагает выбрать сохраняемый ответ. До выбора merge не завершается; скрытого last-write-wins нет. Несовпадающие по event RSVP переносятся. Active reservations обеих identities объединяются; уникальность gift сохраняется. Подписки объединяются по UNIQUE, opt-in не расширяется на другие события. Двойной handoff выполняется безопасно через lock/unique constraints; Telegram identity, уже связанная с другим подтверждённым аккаунтом, не перепривязывается.
Бронирования нельзя автоматически сопоставлять с гостями по имени. Notification consent и organizer role не наследуются от другого человека.
2.4 Матрица доступа и Surprise
Без session: read PublicEventDTO, PublicWishlistDTO и GiftDTO по активному public_id. Запрещены Guests, private profile, внутренние reservation records и любые admin writes.
Guest: всё публичное; read/write own RSVP; reserve available gift; cancel own reservation; opt-in/out own notifications. Запрещены чужие RSVP, чужие имена, admin writes и отмена чужих броней.
Organizer-владелец: CRUD собственного event/gifts; GuestsDTO и totals; настройка wishlist; share link; собственные notification settings. Чужие event IDs возвращают 404. Удаление занятого gift допустимо с confirmation, но не открывает identity брони.
Organizer для чужого события имеет только гостевые права при наличии invitation link и своего guest context.
Surprise ON: OrganizerGiftDTO содержит gift fields + reserved:boolean; отсутствуют reservation_id, guest_identity_id, guest_name, user_id, Telegram ID, subscription ID и timestamps, позволяющие напрямую связать бронь с гостем. Отсутствие полей обеспечивается SELECT/projection backend, а не CSS. Organizer может видеть персональные RSVP как часть Guest List, но API не связывает их с подарками.
Surprise OFF: владелец может получить только reserver_display_name; Telegram/session identifiers по-прежнему не выдаются. Остальные гости всегда видят available/reserved/is_mine и только свою reservation_id. Владелец-гость в Surprise mode видит собственную бронь в гостевом контексте.
GuestList и private DTO: Cache-Control: private,no-store. Public DTO не содержит персональных гостевых данных; is_mine и own RSVP загружаются отдельно и никогда не попадают в shared cache. Базовое правило v1.0 — dynamic/no-store для доступности event/gifts; статические изображения можно кэшировать отдельно.
3. Screen/API mapping
3.1 Общий API-контракт
Префикс /api/v1 для бизнес-API ниже. Auth endpoints из части 2 находятся отдельно в /api/auth и /api/guest. JSON camelCase, DB snake_case; все IDs — opaque strings, даты YYYY-MM-DD, часы HH:mm, timestamps ISO 8601 UTC. Version обязателен для редактирования существующего объекта.
Успех: {data, requestId}. Ошибка: {error:{code,message,fieldErrors?},requestId}. 400 malformed; 401 expired/no session; 403 permission denied; 404 unavailable/not owned; 409 conflict; 422 validation; 429 rate limit; 500 generic. Клиенту не возвращаются SQL, токены или stack traces.
Публичное неизвестное/удалённое event одинаково отвечает 404 EVENT_UNAVAILABLE. Удаление подтверждается UI. Ошибка сети сохраняет форму; retry использует тот же Idempotency-Key. Списки: limit 1..50 DEFAULT 20, opaque cursor, стабильная сортировка created_at+id; Guests фильтр status. Вычисленные totals охватывают весь event, не только страницу.
Проектные rate limits: auth 10/min/IP; guest session 20/min/IP; guest writes 30/min/session плюс 100/min/IP; public reads 120/min/IP. Распределённый limiter; общие сети и Telegram proxy проверяются на QA. Лимиты конфигурируемые.
Публичные event pages используют noindex,nofollow и не входят в sitemap. OG включает title/date/cover, без гостей и Organizer contacts. Referrer-Policy: no-referrer, внешние ссылки noopener/noreferrer. Вывод текста экранируется, пользовательский HTML не исполняется.
3.2 Organizer screens → API → данные
Home / «Мои события» (/) — GET /me и GET /events?bucket=upcoming|past&cursor=… . Читает users, events, агрегаты rsvps; фильтр organizer_id из сессии. Возвращает карточки без данных чужих событий. CTA открывает Create Event.
Create Event (/events/new) — POST /events с title,eventType,eventDate,timezone и optional fields; Idempotency-Key обязателен. Пишет events+wishlists, analytics event_created. Возвращает id,publicId,version,publicUrl. publicUrl строится из настроенного APP_ORIGIN, а не Host входящего запроса.
Event Management (/events/{id}) — GET /events/{id}; GET /events/{id}/summary; GET /events/{id}/guests?limit=3; GET /events/{id}/wishlist. Читает events,rsvps,wishlists,gifts; reservations только через безопасную projection. DELETE /events/{id} выполняет soft delete из 1.10 после подтверждения.
Edit Event (/events/{id}/edit) — GET /events/{id}; PATCH /events/{id} {expectedVersion,fields}. Пишет events; при значимом изменении event_changes и перепланирование N4. Response: event, changeId|null, notificationRecipientsCount. Confirmation отправляет POST /events/{id}/changes/{changeId}/decision {decision:'send'|'skip'}; send создаёт outbox N3; повтор send идемпотентен. Чужой или устаревший changeId → 404/409; stale change не отправляется вместо нового.
Guests (/events/{id}/guests) — GET /events/{id}/guests?status=yes|no|maybe&cursor=…; GET /events/{id}/summary. Read rsvps; GuestListDTO: id,guestName,status,adultsCount,childrenCount,comment,updatedAt. guest_identity_id/Telegram ID не нужны UI и не возвращаются. UI v1.0 не редактирует ответы за гостей.
Wishlist Management (/events/{id}/wishlist) — GET /events/{id}/wishlist; PATCH /events/{id}/wishlist {hideReserverIdentity}; read/write wishlists, gifts; reservation projection согласно Surprise. Переключение OFF требует явного UI-действия с пояснением, что имена станут видны владельцу.
Add/Edit Gift — POST /events/{id}/gifts; GET /events/{id}/gifts/{giftId}; PATCH /events/{id}/gifts/{giftId} {expectedVersion,…}; DELETE тот же endpoint, при занятом gift {confirmReserved:true}. Пишет gifts, отменяет reservations при delete. Проверяется gift.wishlist.event_id, а не только владение event URL.
Share (/events/{id}/share) — GET /events/{id}/share возвращает постоянный publicUrl и preview. Read events; client Web Share/clipboard/Telegram механизм. POST /analytics с event_shared — пользовательское действие, не доказательство доставки приглашения.
Profile/settings — GET /me; GET /events/{id}/notification-subscription; PUT тот же endpoint {enabled}. Read users,telegram_channels; write organizer notification_subscriptions. Если канал не ready, показывается opt-in flow. POST /api/auth/logout отзывает текущую organizer session.
3.3 Guest screens → API → данные
Public Event (/e/{publicId}) — GET /public/events/{publicId}. Read events и cover media; PublicEventDTO содержит только публичные поля события. GET /public/events/{publicId}/my-context возвращает own RSVP и notification setting при session либо {rsvp:null,notificationsEnabled:false}; ответ no-store. Просмотр отправляет event_opened с anonymous visitor id, без персональных полей.
RSVP bottom sheet — при отсутствии session POST /api/guest/session; PUT /public/events/{publicId}/rsvp {guestName,status,adultsCount,childrenCount,comment,expectedVersion?}. Read/write rsvps, guest identity name; outbox N1/N2 для subscribed Organizer; серверная analytics. GET /public/events/{publicId}/rsvp возвращает только собственный ответ. expectedVersion требуется при изменении, null для создания; отсутствие строки с expectedVersion → 409.
RSVP Success — использует result PUT, не повторяет запись. CTA: guest wishlist и opt-in Telegram. При refresh собственный ответ читается из my-context.
Guest Wishlist (/e/{publicId}/wishlist) — GET /public/events/{publicId}/wishlist. PublicDTO: hideReserverIdentity не требуется; gifts{id,title,imageUrl,amount,currency,comment,externalUrl,reserved}. GET /public/events/{publicId}/my-reservations добавляет isMine только текущему гостю. Read wishlists,gifts,reservations; analytics wishlist_opened.
Gift Details — GET /public/events/{publicId}/gifts/{giftId}. Проверяет принадлежность активному event. Read gift+reserved; own context отдельно. Внешний URL открывается клиентом, сервер не делает auto-scraping.
Reservation modal — POST /public/events/{publicId}/gifts/{giftId}/reservation {guestName?}, Idempotency-Key. При отсутствии RSVP имя обязательно; имя не означает автоматически yes. Write guest identity, reservation; return own reservationId, giftId, reservedAt. Race → 409 GIFT_ALREADY_RESERVED и обновление карточки. DELETE тот же endpoint отменяет только свою active reservation; повтор отмены возвращает успешное отсутствие active reservation.
Guest notification opt-in — POST /public/events/{publicId}/notification-handoff; затем подтверждённый Telegram flow из 2.3. GET /public/events/{publicId}/notification-handoff/{handoffId} только исходной сессии; PUT /public/events/{publicId}/notification-subscription {enabled:false} отключает подписку. Enabled=true разрешён только связанному Telegram principal после согласия и готового канала. Read/write handoffs,identities,channels,subscriptions; новая подписка планирует N4, если момент ещё впереди.
Map / route — read venue,address,coordinates из EventDTO; кнопка строит URL внешнего сервиса. POST /places/search доступен только Organizer, proxy Mapbox autocomplete; ручной адрес всегда допустим. Координаты сохраняются через PATCH event. Цены/лимиты провайдера не фиксируются как гарантия бюджета.
3.4 Служебные endpoints и DTO-примеры
Media: POST /media/uploads {mimeType,byteSize} → signed upload; POST /media/{assetId}/complete → проверка/перекодирование → ready. Upload принадлежит Organizer, прикрепление через event/gift mutation.
Telegram: POST /api/telegram/webhook проверяет секрет, фиксирует update_id, обрабатывает /start opt-in/handoff и блокировки. Internal worker endpoint защищён секретом scheduler, доступ клиентам закрыт. Send только из outbox.
POST /analytics принимает allowlisted события и schema properties; server principal не принимается из body. Собственные бизнес-события клиент не может подменять как источник истины.
PublicEventDTO пример: {publicId,title,eventType,eventDate,startTime,endTime,timezone,venueName,address,coordinates,directions,description,dressCode,coverUrl,hasWishlist}. Ни organizerId, ни контактов.
GuestGiftDTO пример: {id,title,amount,currency,imageUrl,externalUrl,comment,reserved}; OwnReservationDTO: {reservationId,giftId,reservedAt}. OrganizerGiftDTO в Surprise: {id,title,…,reserved,version}, без reserver fields.
SummaryDTO: {responses:{yes,no,maybe,total},confirmed:{adults,children},gifts:{total,reserved}}. Суммы подтверждённых гостей не смешиваются с числом RSVP.

4.3 Обязательные проверки и Definition of Done
Security: cross-owner event/gift IDs; direct DB anon read; forged initData; expired OIDC/session; replay handoff; CSRF; GuestList leakage; Surprise API/лог/analytics leakage; unsafe URL и upload.
Concurrency: два reserve одного gift; повтор одного reserve; одновременный RSVP update; optimistic event edit conflict; delete event/gift одновременно с reserve; merge identities с конфликтным RSVP; два worker с одним outbox row.
Notifications: opt-in отсутствует; bot blocked; retry/429; worker crash после send; edit send/skip; reschedule; event без времени; yes/maybe/no; event deletion; opt-out; expired handoff. Нельзя имитировать Telegram delivery только записью status=sent — staging smoke test с реальным ботом обязателен.
Cross-platform: Mini App → Browser OIDC → PWA с тем же user; anonymous RSVP → refresh → edit; browser opt-in → Telegram на втором устройстве; имена кириллицей; разные timezone и DST; одинаковая дата без start_time.
Alpha DoD: реальный Organizer входит через Telegram, создаёт событие, добавляет подарки, отправляет ссылку; Guest открывает без регистрации, отвечает RSVP, резервирует подарок, подключает Telegram; Organizer видит ответ и получает N1/N2; Guest получает N3 после send и N4 по расписанию. Повторные запросы, refresh и конфликт брони не портят данные. Всё работает на production-like среде с единой БД.
Public MVP DoD: Alpha DoD + P1, проверенный rollback/restore, базовая privacy/retention документация, мониторинг worker, отсутствие критических дефектов безопасности и потери данных. Оценки сроков выставляются командой после B01/B02; последовательность и критерии выше являются обязательным контрактом реализации.
